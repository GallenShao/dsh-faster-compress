# dsh-faster-compress

上下文压缩不再打断 agent。

[English](README.md)

## 问题

[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 自带的压缩后端在 `agent/pre-step` 钩子里生成摘要，并且等它写完才放行。下一次模型请求必须等摘要产出，于是会话恰好在撑不住的那一刻停住：agent 空转，你没法插话，唯一在发生的事情是摘要正在被写出来。

## 改了什么

摘要在会话继续跑的同时生成，替换动作留到 step 边界再做。

```
改造前   ── 请求 ── 工具 ── [====== 摘要 ======] ── 请求
                                 ↑ agent 在这里干等

改造后   ── 请求 ── 工具 ── 请求 ── 请求 ── …
                     └─ [后台生成摘要] ─┐
                                       └─ 在下一个 step 边界提交
```

支撑这个改动的三个判断，各自都有理由：

**提前生成，按时提交。** 压缩一旦提交，会话前缀就被替换了， provider 缓存的那段前缀对后续所有请求随之失效。摘要一好就提交，等于比必要时间更早地把"命中的缓存前缀"换成"全价 prefill"。所以摘要在压力越过提前阈值（默认为提交阈值的 85%）时就开始准备，但替换真正落地要等到压力抵达原版后端会用的那个阈值。

**在 step 边界提交。** 那里 surface 是静止的：上一个 step 已经收尾，下一个请求还没开始推导。在请求中途提交，会让一个已经发出去、按旧前缀计费的请求被留在改写后的前缀后面。

**沿用原版的事务。** 提交时追加的还是那四条事件——兼作压缩锁的起始括号、带影子价格的摘要记录、表层替换、结束括号。回放、计价、压缩不变量、崩溃恢复的行为与未安装本 bundle 时完全一致。摘要在"仅仅正在生成"的阶段不写任何会话日志，所以被丢弃的摘要不留痕迹，压缩锁也不会横跨一段后台等待。

两个配套细节：

- **优先用工具执行窗口触发。** 工具调用是最好的起点：结果落地之前 surface 不动，模型也没在解码，而且工具通常跑得足够久，摘要能在下一个 step 边界之前完成。对于很少有长工具的会话，压力阈值作为兜底仍然生效。
- **预热，可选。** 提交后的第一个请求发的是一段新前缀，匹配不到任何缓存条目，因此要为"摘要 + 保留尾部"付一次完整 prefill。开启 `warmup` 后，同样的前缀会在工具执行期间以一个极小的生成长度先发一次，把这段 prefill 挪到没人在等的时刻。计算量没有增加，只是提前了。

替换只遮蔽选中的区间，所以摘要生成期间到达的消息照常可见，也不会让摘要失效。提交后的历史就是摘要紧跟被遮蔽区间之后的一切——这本来就是原版后端投影一次压缩的方式。

## 安装

走插件管理页：**插件 → 安装 bundle**，安装标识填 `github:<你的仓库>/dsh-faster-compress`、registry 包名，或一个打包好的 tgz 路径（在本目录执行 `npm pack` 即可生成）。

请用 tgz、registry 或 GitHub 安装，不要直接指向检出的目录。指向本地目录的安装会把包 link 到 profile 依赖树之外，`@deepseek-ai/*` 这些 peer 包在那里解析不到；实测结果是这一行以 `failed to import` 收场。基于复制的安装（registry、GitHub、tgz）会把包放进依赖树并链好 peer，这才是本 bundle 需要的方式。

bundle 会禁用自带的 `compaction-basic` 行，在原位挂载它的子类。子类把自己注册为 `compaction` 服务，所以 `/compact`、工具结果裁剪、图片卸载都不需要额外改动。

## 配置

所有字段都可省略。原版后端的字段照旧可用、语义不变；本 bundle 新增四个：

| 字段 | 默认 | 含义 |
| --- | --- | --- |
| `eagerRatio` | `0.85` | 压力达到提交阈值的这个比例时开始提前生成。取值 0 到 1 之间。 |
| `warmup` | `true` | 在工具执行期间预热提交后的请求前缀，让提交不必付冷启动 prefill。 |
| `warmupMaxTokens` | `1` | 预热请求的生成长度上限。 |
| `maxConcurrent` | `1` | 同一主机上所有会话合计允许并行生成的摘要数。 |

```yaml
- id: compaction-basic
  disabled: true

- insert:
    - id: faster-compress
      name: 'dsh-faster-compress'
      config:
        eagerRatio: 0.8
        maxConcurrent: 2
        # 原版字段照常生效
        thresholdRatio: 0.8
        headroomTokens: 32768
```

如果推理端点的缓存驱逐快过"预热到提交"之间的间隔，预热就成了纯开销，这时把 `warmup` 设为 `false`。`maxConcurrent` 只在端点确实有余力时再调高；本机共用一个模型时保持 1，免得和你正想保住速度的那一轮抢资源。

## 它不做什么

- **不消除压缩本身必然带来的 prefill。** 用摘要替换历史会改变请求前缀，这段新前缀的第一个请求必须 prefill。预热把这笔开销从你等待的路径上挪开，没有把它变没。
- **不改变摘要质量。** 压缩指令、检查点框定文案、保留预算都来自原版后端。
- **不会在提前阈值之下压缩。** `/compact` 的行为和以前一样。

## 已知的取舍

- **预热请求会发出可能永远不落日志的模型可见文本。** 预热前缀里含检查点文本，而这段文本只有在提交真的发生时才写进会话日志。如果准备好的摘要最终被丢弃，那次请求的内容除检查点框定外仍可从日志重建。若你要求每一个发给模型的字节在发出的瞬间就已持久化，把 `warmup` 设为 `false`。
- **准备好的摘要会失效。** 摘要生成期间选中区间被改写——通常是工具结果裁剪重新定了它的价格——摘要就被丢弃，压缩回退到同步路径。这种情况下白跑一次摘要。
- **`eagerRatio` 要为测量误差留余量。** 压力读数由 provider 上报的 usage 锚点加上锚点之后内容的字符密度估算构成，后者按字符数除以 4，对中日韩文本明显低估。提前阈值贴提交阈值太近，可能启动得太晚而起不到作用。
- **验证基于 `@deepseek-ai/dsh@0.2.0-rc.2`。** bundle 依赖文档化的子类钩子 `summarize()` 和已解析配置的字段形状。这两者一旦变动，表现为加载或提交失败，不会静默跑偏。

## 开发

没有构建步骤，bundle 直接发布它运行的 JavaScript。peer 包都在 npm 上，装好就能开发。

```sh
npm install
npm test    # 阈值计算与区间选择
npm run check
```

模块划分：

| 文件 | 职责 |
| --- | --- |
| `src/index.js` | 引擎：何时生成、何时提交、何时丢弃 |
| `src/budgets.js` | 阈值计算，不 import 任何东西，可单独测试 |
| `src/selection.js` | 区间选择与稳定性校验，保证工具调用配对平衡 |
| `src/checkpoint.js` | 检查点框定，以及请求前缀的重建 |
| `src/transaction.js` | 四条事件的 durable 提交 |

`src/budgets.js` 和 `src/selection.js` 重新推导了上游包没有导出的公式。它们与上游 `packages/compaction/compaction-basic/src/{config,region}.ts` 的对应关系靠注释维护，而不是靠 import，这样上游的内部重构不会让这个 bundle 静默算错。两者都有测试覆盖，包括会话末尾有一个尚未收到结果的工具调用、必须留在被遮蔽区间之外的情形。
